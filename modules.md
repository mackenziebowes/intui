## crates/intui-layout/src/chart_scale.rs
Chart scales: a readable y range, short axis numbers, which x labels fit.

## crates/intui-layout/src/flow_analysis.rs
Flow layering: which column each step sits in, and which links close a loop.

## crates/intui-layout/src/lib.rs
The data math every IntUI renderer shares, ported from `packages/layout`: chart scales, how a Flow is layered, how typed numbers are read, and the marks a reading wears.

## crates/intui-layout/src/logic.rs
Small decisions renderers share: column alignment, typed numbers, a chart read aloud, the mark before a reading, how a change points.

## crates/intui-layout/src/main.rs
`intui-layout`: answers layout questions from JSON, so a check can put the same questions to core's TypeScript and to this port and compare.

## crates/intui-text/src/lib.rs
The text form of a tree: the same Markdown core's `Tree.toText()` writes.

## crates/intui-text/src/main.rs
`intui-text`: reads a tree as JSON on stdin and prints its text form.

## crates/intui-text/src/numbers.rs
Numbers written the way JavaScript writes them.

## crates/intui-text/src/text.rs

## crates/intui-text/src/words.rs

## crates/intui-types/build.rs
Generates Rust types from core's committed JSON Schemas with typify, so the protocol is defined once, in TypeScript. Formatted with prettyplease, so a clean `cargo build` needs no rustfmt on the machine.

## crates/intui-types/src/edge.rs
The edge: the one place JSON from a wire becomes a `Tree`.

## crates/intui-types/src/lib.rs
The IntUI tree as Rust sees it: types generated from core's committed JSON Schemas, and the one edge that turns JSON from a wire into a `Tree` or a `Refusal`.

## crates/intui-types/src/node.rs
The parsed tree: what `parse` hands the rest of the program.

## crates/intui-types/src/reading.rs
A number and how sure it is: the Rust side of core's `Reading`.

## crates/intui-types/src/refusal.rs
Why a tree was refused, in one catalogue.

## crates/tests/acceptance_parity.rs
Acceptance parity: Rust refuses the trees core refuses, with the same places and (where core's advice is formulaic) the same words, and accepts the trees core accepts. A kind this build has never heard of is the one deliberate difference: Rust draws around it.

## crates/tests/common/mod.rs
What every parity check shares: running core's side (a bun script) and Rust's side (a built binary).

## crates/tests/core/acceptance.ts
Prints core's verdict on every tree: `{ accepted: [...names], refused: [{ name, json, words, message }] }`.

## crates/tests/core/layout.ts
Prints `{ cases, answers }`: the layout questions the parity check puts to Rust, and what `packages/layout` answers to each, in the same shape `intui-layout` prints.

## crates/tests/core/newer-trees.ts
Prints the trees that hold a kind core has no component for, and whether core takes them (it must not).

## crates/tests/core/text-forms.ts
Prints core's text form of every accepted tree: `[{ name, json, text }]`.

## crates/tests/core/trees.ts
Trees the parity checks put to core and to Rust. A tree is JSON text, so a value like -0 (which JSON.stringify would lose) reaches both sides as written.

## crates/tests/layout_parity.rs
Layout parity: `intui-layout` answers every question the way `packages/layout` does: nice chart ranges and steps, axis numbers, which labels fit, how a Flow is layered and its cycles broken, how typed numbers are read, and what a change points at.

## crates/tests/text_parity.rs
Text-form parity: `intui-text` prints, byte for byte, what core's `Tree.toText()` writes.

## evals/run.ts
Runs the eval cases: asks headless Claude Code each question with the plugin loaded and records what happened: every show call (drawn or refused, and why), the components in it, and the reply's text. Nothing is graded. A case's `expect` is a hope to read the record against, by eye, as a trend over runs (the eval-design skill). Each run writes evals/results/<date>-<model>.jsonl.

## packages/core/schema.ts
Writes core's JSON Schemas to `packages/core/schema/`, the files other languages generate their types from, so the TypeScript here stays the one definition. `--check` writes nothing and exits 1, naming the file and the command to run, when a committed copy no longer matches core. The committed schema gives the shape; `Tree.parse` gives the verdict, including the cross-field rules a schema can't express.

## packages/web/build.ts
Builds the browser files into packages/web/dist: intui-web.js ES module: render, textOf, markdownToHtml (core and marked bundled in) intui-web.css the stylesheet intui-page.css the opt-in page shell (background, width, gutter) for pages made only of trees demo.html every core component's example at three widths; open it from disk

## packages/web/demo/demo.ts
The demo page: every core component's example at three widths, plus a few harder trees, so a person can check the look in light and dark. `?theme=dark` or `?theme=light` forces a theme; otherwise it follows the system.

## packages/web/e2e/browser.test.ts
@intui/web in a real browser: the renderer bundled as a host page bundles it, opened in headless Chromium by agent-browser, and driven with real clicks and typing. Checks the contracts a host relies on: what reaches `onEvent`, that a used-up control can't fire again, and that Markdown can't run code.

## packages/web/e2e/page.ts
The page the browser checks drive: a few trees drawn by the real renderer, each in its own section. Events land in `window.intuiEvents` as JSON, so a check reads exactly what a host's `onEvent` received.

## packages/web/src/chart-layout.ts
Pure geometry for the SVG Chart: where every tick, bar, line point, label and marker goes at a given pixel width. The drawer turns it into elements; the look (colours, dashes) is the stylesheet's job, keyed on each series' role.
