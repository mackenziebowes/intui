# Modules

Generated by modmap from each module's opening paragraph. Don't edit; edit the header, then run `modmap write`.

## crates/intui-egui/src/controls.rs
The state of every control the person has used, in the control machine `intui-types` shares with core (hub #1956), kept per (Source, control id), and what they have typed into a form that isn't sent yet.

## crates/intui-egui/src/draw/chart.rs
Chart: a line or bar plot drawn on egui's painter at the width it is given. Every position comes from `intui-layout` (the scale, the axis numbers, which x labels fit, the marker glyphs); this file only turns them into shapes. A point that is a floor wears a small chevron above it, an estimate is hollow or faded, an unknown one is a cross at the foot of its x, and a gap in the data breaks a line. A chart with no number to plot says so.

## crates/intui-egui/src/draw/choice.rs
Choice: buttons that send an event. A `once` choice is used up after one answer and shows what was chosen; a refused press shows the app's words by the control and the buttons work again.

## crates/intui-egui/src/draw/figure.rs
Label and Stat: a tone drawn as a small tag, and a figure whose reading says how sure it is: `≥` before a floor, `~` before an estimate, and a dash with the word "unknown" where no number could be read.

## crates/intui-egui/src/draw/flow.rs
Flow: steps as boxes in layers, with arrows between them. The layering comes from `intui-layout` (`analyse`), which also says which links close a loop. Layers run left to right when every one gets room; otherwise the steps stack in one column in layer order. A link an arrow would have to cross boxes for, and every link back, is written in its source box instead, so no arrow ever runs through a step.

## crates/intui-egui/src/draw/form.rs
Form: fields the person fills in, checked before anything is sent. A required field left empty, or a number field holding something that isn't a number, sends nothing and says which field and why; a refused submit keeps what the person typed; a sent form shows what it was sent with and can't be sent again.

## crates/intui-egui/src/draw/group.rs
Group: children in a column, or in a row that wraps when it gets narrow. Each child of a row gets an equal share of the width, but never less than its kind needs (a line of text less than a block of it), and the row breaks onto a new line instead of squeezing a child below that.

## crates/intui-egui/src/draw/mod.rs
One module per kind, each drawing its kind on egui's painter and basic widgets and naming itself to accessibility.

## crates/intui-egui/src/draw/table.rs
Table: a header that stays put over rows drawn only when they are on screen, so a table of thousands of rows costs what the window shows. Columns that are all numbers align to the right unless the column says otherwise, and a table wider than its place scrolls sideways instead of clipping.

## crates/intui-egui/src/draw/text.rs
Text: Markdown drawn from `pulldown-cmark`'s events with egui's painter. Code scrolls sideways and never clips, and links open only when their address is http, https or mailto.

## crates/intui-egui/src/draw/unknown.rs

## packages/claude-code/src/tool.ts

## packages/claude-code/src/usage.ts

It keeps counts and component names, never content, and old entries missing newer fields still summarize.

## packages/core/checks/control-parity.ts
The control machine, core against the Rust crates (hub #1956): each event sequence is replayed through core's `stepControl` and through the `intui-control` binary, and the lines they print must be byte for byte the same. Run after `cargo build -p intui-event` (in crates/): bun packages/core/checks/control-parity.ts Exits 1 on the first difference. It drives the real binary, so it checks what ships.

## packages/core/checks/marks-parity.ts
Marks and Ladder, core against the Rust crates (proposal 005): the text form of each example and the refusal for each bad tree must be byte for byte the same in both. Run after `cargo build -p intui-text`: bun packages/core/checks/marks-parity.ts Exits 1 on the first difference. It drives the real `intui-text` binary, so it checks what ships.

## packages/core/schema.ts
Writes core's JSON Schemas to `packages/core/schema/`, the files other languages generate their types from, so the TypeScript here stays the one definition. `--check` writes nothing and exits 1, naming the file and the command to run, when a committed copy no longer matches core. The committed schema gives the shape; `Tree.parse` gives the verdict, including the cross-field rules a schema can't express. Each kind's `$defs` entry carries `x-intui-writer` (`anyone` or `code`), the rule that decides which trees a model may author.

## packages/core/src/catalog.ts
A Catalog is a set of component kinds and the schemas for trees built from them, as plain data with its functions on `Catalog` (hub #1956); `core` holds every component IntUI defines. It knows who may write each kind (`model` or `code`), so a tree is checked against the author, and it makes the JSON Schema and the one-line descriptions a tool shows a model.

## packages/core/src/component.ts
What a component kind is: its schema, who may write it, its text form, the children and ids it holds, and a valid example. Every kind has a text form, which is what the model reads back and what any surface that can't draw it falls back to.

## packages/core/src/components/chart.ts
The Chart component: bars or lines over named x positions, one or more series, and markers. Only code may write it, since it shows numbers; each point is a Reading, so a floor, an estimate or a missing value is told apart from an exact one in the text form as well as the drawing.

## packages/core/src/components/choice.ts
The Choice component: a prompt and two or more options the person can press, each with an id that comes back in the event. A choice is `once` (used up after a press) or `many`; the option ids are what the agent receives, the labels what the person sees.

## packages/core/src/components/flow.ts
The Flow component: steps joined by links, for a process or a dependency order. With no links each step leads to the next. A link naming a step that isn't there is refused with the path and the ids that exist.

## packages/core/src/components/form.ts
The Form component: fields (text, number, select, checkbox) the person fills in and submits, with an id the submit event carries back. A select without options is refused, and its text form lists each field and whether it is required.

## packages/core/src/components/group.ts
The Group component: other components in a row or a column, nested to any depth. Its text form joins its children's text forms.

## packages/core/src/components/label.ts
The Label component: a short tag whose tone says what it means (neutral, positive, warning, critical, muted). Each renderer decides how a tone looks; the text form is the text in brackets. Also holds the list of tones, which Stat reuses.

## packages/core/src/components/ladder.ts
The Ladder component (proposal 005): stages from the bottom up, each holding nodes with marks in them, and counted steps between nodes. A node can say its count in text (when there are too many marks to show one by one) or say it is unknown with the reason, never zero. Only code may write it.

## packages/core/src/components/marks.ts
The Marks component (proposal 005): rows of small marks, one per thing counted, for counts small enough to show one by one. A mark has a kind (what it is: a person, a visit; the first kind is drawn filled, the second hollow, the third as a ring) and optionally a state (how far it got). A row can carry a halo, an amount around the row that is not a mark, and can be unknown, said with its reason so it is never drawn as zero. Only code may write it, since it shows numbers. This file also holds the pieces Ladder shares: the mark, the kinds, the states and the counts text.

## packages/core/src/components/stat.ts
The Stat component: one figure with a label, a unit and an optional change. Only code may write it. The value and the change are Readings, so a floor, an estimate or an unknown shows as one and never as a bare number.

## packages/core/src/components/table.ts
The Table component: named columns and rows of cells keyed by column. A row key that names no column is refused with the path and the keys that exist; a missing cell is empty, never 0. Its text form is a Markdown table.

## packages/core/src/components/text.ts
The Text component: Markdown prose. Its text form is the Markdown itself, and it may not be empty.

## packages/core/src/control.ts
A Choice or Form being answered, as one state machine every renderer shares (hub #1956): read-only, ready, sending, sent or refused. `stepControl` is the only transition: a surface sends the person's answer and the host's verdict in as events, runs the effects it returns, and paints the state. An answer that doesn't fit the control is refused here with core's words, and an event a state can't take comes back ignored with the reason, so no surface checks or decides anything itself.

## packages/core/src/event.ts
What a person did with a component: pressed a Choice option or submitted a Form, as an `IntuiEvent` the host sends back to the agent. An event names the tree's source and the component's id, and is parsed at the edge like a tree, so one that doesn't fit is refused with every problem listed.

## packages/core/src/index.ts
The public face of `@intui/core`: the tree, the catalog and every component, readings, events and refusals, and the text helpers. Everything a renderer or a host imports comes from here.

## packages/core/src/problems.ts
Turns a schema failure into problems a model can act on: each names a path inside the tree (`root.children[1] (Chart).series[0]`), the rule that failed and what to do. A `Refusal` carries all of them, and one message listing them, so one retry can fix everything. Parsing returns `Parsed<T>`, a value or a refusal, and never throws (hub #1956).

## packages/core/src/reading.ts
A Reading is a number and how sure it is: exact, at least, an estimate, or unknown. An unknown holds no number, so it can never pass for 0, and a bare number on the wire means exact so older trees keep their meaning. This module parses readings, says them in words, and turns them back into wire form.

## packages/core/src/text.ts
Small helpers for the Markdown text forms.

## packages/core/src/tree.ts
A Tree is a validated component tree, the thing an agent shows on any surface, as plain data with its functions on `Tree` (hub #1956). `Tree.parse` takes whatever crossed a wire and returns the tree or a refusal listing every problem, checking who wrote it; `Tree.of` takes one code built. It also renders the text form, finds the interactive components by id, and checks that an event answers something in this tree.

## packages/layout/src/chart-scale.ts
The geometry of a Chart that doesn't depend on how it is drawn: categories in order, round axis domains and steps, which x labels fit, and the numbered markers. Both the terminal and the web chart are drawn from this one model, so they agree on what each point is.

## packages/layout/src/flow-analysis.ts
Works out a Flow's structure before it is drawn: links resolved to step indexes, cycles broken into forward and back edges by a depth-first walk, and steps put in layers. It always finishes, whatever the links.

## packages/layout/src/index.ts
The public face of `@intui/layout`: the chart model, flow analysis and the small shared rules both renderers use.

## packages/layout/src/logic.ts
Small rules every renderer must agree on: which way a column aligns, how a typed number is read (a typo is a note, never silently empty), how a chart is described to a screen reader, and how a Stat's change points. A floor and an estimate carry their marks (`≥`, `~`) and an unknown carries none.

## packages/web/build.ts
Builds the browser files into packages/web/dist: the library, its stylesheets and the demo page.

## packages/web/demo/demo.ts
The demo page: every core component's example at three widths, plus a few harder trees, so a person can check the look in light and dark. `?theme=dark` or `?theme=light` forces a theme; otherwise it follows the system.

## packages/web/src/chart-layout.ts
Pure geometry for the SVG Chart: where every tick, bar, line point, label and marker goes at a given pixel width. The drawer turns it into elements; the look (colours, dashes) is the stylesheet's job, keyed on each series' role.

## packages/web/src/dom.ts
The browser renderer's building blocks: `Dom` builds HTML and SVG elements in one document, and `DrawContext` is what each drawer gets besides its props (child drawing, the host's event handler, pressed and submitted state, width and text measuring). A drawer is a function from props and context to an element.

## packages/web/src/draw/basic.ts
The browser drawers for the display components: Text, Group, Label, Stat and Table. A table with many columns becomes one card per row when narrow, and a Stat's reading wears its floor or estimate mark with words a screen reader says.

## packages/web/src/draw/chart.ts
The browser Chart drawer: an SVG plot redrawn at the element's width, with a legend, numbered markers, a label for screen readers and the chart's text form under a disclosure. Readings that are floors, estimates or unknown are drawn as such, and a gap in the data breaks a line.

## packages/web/src/draw/controls.ts
The browser drawers for the controls, Choice and Form. Each is a surface on core's control machine (`stepControl`, hub #1956): a press or submit goes in as an event, the host's verdict goes in as accepted or refused, and `paint` draws whatever state comes out. The machine decides when a control is used up, busy or read-only; nothing here does.

## packages/web/src/draw/flow.ts
The browser Flow drawer: steps as boxes laid out by CSS, with the arrows drawn as SVG from the boxes' measured positions and redrawn when the width changes. The full list of links is kept in the DOM order for screen readers.

## packages/web/src/draw/marks.ts
The browser drawers for Marks and Ladder (proposal 005): one glyph per thing counted, so a count of seven looks like seven. The first kind is drawn filled, the second hollow, the third as a ring; a state's tone colours the glyph. Above THIN marks a field is a count in text and a band instead of glyphs (points are for small numbers). Nothing needs a hover: details are listed under the row. Glyphs may drift a little, and are still under prefers-reduced-motion (style.css).

## packages/web/src/flow-layout.ts
Pure layout for the web Flow: which way the layers run at a given width, and the connector between two measured boxes. The boxes themselves are laid out by CSS; the drawer measures them and asks `connector` for each arrow.

## packages/web/src/form-values.ts
Turns what is in a Form's controls into the values an event carries, or says what to fix first: empty optional fields are left out, numbers that don't parse are named, checkboxes are always sent. Field ids are kept without a prototype, so a field called `constructor` is an ordinary field.

## packages/web/src/index.ts
The public face of `@intui/web`: `render` draws a parsed tree as DOM, `textOf` gives a node's text form, and `markdownToHtml` is the safe Markdown renderer.

## packages/web/src/markdown.ts
Markdown to HTML for Text components. Trees can come from a model, so the output is always safe to put in `innerHTML`.

## packages/web/src/paths.ts
Where the built files are on disk, for a server that serves them (the hub). Not for the browser: import `@intui/web` there, and link the stylesheet.

## packages/web/src/render.ts
`render` draws a parsed Tree as one detached `<div class="intui">` for the host to place, in light or dark, with every Choice and Form reporting to the host's `onEvent`. A drawer that throws shows that node's text form instead, and a kind with no drawer is drawn as its text form, so a valid tree never comes out blank.
